# W1 NFC Reader v2.1 — Real-time / UTC timeline and coverage UX

Status: planned canonical product direction for v2.1.0. Implementation details remain subject to evidence and testing.

## Problem

W1 archive records currently use meter-local/floating logger wall-clock timestamps, while Live reads use Android/device acquisition time. A meter clock can differ materially from real local time. This creates two user-facing problems:

1. History/Statistics navigation by clock time can select the wrong archive bucket from the user's perspective.
2. A future Home Assistant integration would produce misleading statistics/correlations if archive records were published with raw meter wall-clock timestamps instead of real absolute timestamps.

At the same time, raw meter wall-clock time remains valuable for technical users who deliberately want to navigate and inspect the timeline exactly as the meter itself recorded it.

## Product rule

v2.1 shall preserve both time representations and let the user choose a **global app time basis**:

- **Local time (recommended)**
- **Meter time**

The choice changes presentation and History/Statistics navigation semantics, but never destroys or rewrites the underlying raw meter evidence or canonical UTC mapping.

### Local time mode

The user-facing primary timeline is real local time derived from a canonical UTC timeline.

- User-entered History/Statistics ranges are interpreted in the local time assigned to the relevant meter.
- Archive records retain raw meter-time evidence but receive separate derived UTC interval boundaries when evidence is sufficient.
- History cards show real/local time as the primary time and raw meter time as secondary technical evidence.
- Navigator/custom-range input is converted from the meter-assigned local zone to UTC before overlap/containment evaluation.
- Coverage semantics described below apply when real requested boundaries do not line up exactly with archive bucket boundaries.

### Meter time mode

The raw meter/logger wall-clock becomes the primary app timeline.

- History cards show raw meter time as the primary time.
- Real/local time is shown as secondary information when a trustworthy UTC mapping exists.
- History/Statistics navigator and custom-range input are interpreted directly on raw meter/logger wall-clock time.
- Do not silently convert a meter-time request to real/local time first.
- If meter clocks differ across meter replacement, raw meter-time mode may contain an intentional discontinuity at the lifecycle boundary. Never smooth or invent continuity across meters.

### Global preference

The time-basis preference is global for the Android app so History, Statistics and Live presentation stay consistent across screens.

Conceptual preference:

- `LOCAL`
- `METER`

Recommended/default value: `LOCAL`.

The preference is a UI/query projection only. It must not mutate persisted raw timestamps, meter evidence, derived UTC fields or integration-facing data.

## Meter-assigned local timezone

For v2.1, **local time means local civil time in the timezone assigned to that physical meter**, not simply whatever timezone the phone happens to use later.

### Initial assignment

At the first successful verified Live/default read for a meter that has no assigned timezone yet:

- read Android's current IANA `ZoneId` / timezone identifier, for example `Europe/Berlin`;
- persist that timezone for this meter;
- record provenance such as `DEVICE_AT_FIRST_VERIFIED_LIVE`;
- no GPS/location permission is required or desired for this assignment.

Do **not** persist only the current numeric UTC offset such as `+02:00`. Persist an IANA zone ID so historical DST rules remain available.

Conceptual fields may include:

- `meter_zone_id`;
- `meter_zone_source`;
- `meter_zone_assigned_at_utc`;
- optional validation/quality state.

### Stability and user correction

Once assigned, the meter timezone must not automatically change merely because:

- the user travels;
- Android changes its current timezone;
- a backup is opened on another device.

The user must be able to review and change the assigned meter timezone in Settings or Meter details.

Changing the assigned timezone may trigger re-resolution/re-indexing of **derived** local/UTC presentation data where appropriate, but must never rewrite the raw meter/logger timestamp evidence.

### Plausibility / quality

The first Live read also provides evidence that can help assess the assignment:

- Android acquisition UTC;
- Android ZoneId;
- meter wall-clock;
- SU/summer-time flag;
- On-Time;
- meter identity.

If these conflict materially, mark the real-time mapping quality accordingly rather than pretending the mapping is certain.

If a v2.0-origin meter has no timezone assignment after migration/restore, v2.1 may assign it on the next successful verified Live read or allow explicit user selection.

## Settings UX

Settings shall expose a dedicated time-basis section with clear explanatory copy.

Suggested structure:

### Time basis

**Local time (recommended)**

Use the meter's assigned local timezone for primary display, History navigation and Statistics. The meter's own clock remains visible as secondary technical information. If real time cannot be resolved reliably for a record, the app does not guess.

**Meter time**

Use the time stored by the water meter for primary display, History navigation and Statistics. If the meter clock is fast or slow, these periods can differ from real local time. Resolved local time remains visible as secondary information where available.

Also expose the meter's assigned timezone, for example:

- `Europe/Berlin`
- source: assigned from Android at first verified Live read
- action: change timezone

The wording should be localized and user-facing; IANA identifiers may be shown as technical/detail information while a friendly localized timezone label is used where practical.

## Live presentation

The selected app time basis applies to Live presentation as well.

### Local time mode

- primary: Android/real acquisition local time in the meter-assigned timezone;
- secondary: meter wall-clock time.

### Meter time mode

- primary: meter wall-clock time;
- secondary: real/local acquisition time.

This preserves the same mental model across Live, History and Statistics.

## Evidence model

Never overwrite or discard the original meter evidence.

Preserve at minimum:

- raw meter logger wall-clock timestamp;
- Type-F summer-time/SU flag;
- On-Time evidence;
- meter identity;
- archive family/granularity;
- acquisition/retrieval evidence;
- meter-assigned IANA timezone + provenance;
- raw validation/quality state needed to explain the derivation.

Derived time fields should be separate, for example:

- `derived_start_utc`;
- `derived_end_utc`;
- `time_derivation_method`;
- `time_quality` / uncertainty;
- anchor identity.

A simple fixed `meter offset` must not be used as the canonical long-term model. Clock drift, DST transitions, meter replacement and On-Time discontinuities must be handled explicitly.

## Real-time anchors

A successfully verified Live/default read can provide a strong anchor because the app knows both:

- Android/device acquisition time as an absolute real timestamp;
- Android ZoneId assigned to the meter when appropriate;
- meter wall-clock time and SU flag;
- On-Time.

Historical archive times should preferably be resolved against validated anchors using monotonic On-Time differences where this is proven safe.

DST/SU evidence remains important, especially around repeated or skipped local wall-clock hours.

## History UX — Local time mode

History must show every archive interval that overlaps the requested real-time range.

Example requested real range:

- 17:00–18:00

Available real archive intervals:

- 16:55–17:55
- 17:55–18:55

History should show both rows. The partially overlapping status should be understandable without exposing protocol details, e.g.:

- primary: `16:55–17:55 · Hour`
- secondary: `Meter time: 16:00–17:00`
- state: `Partly inside selected range`

The selected user range itself must never be silently shifted to match meter buckets.

## History UX — Meter time mode

History navigation uses the raw logger wall-clock directly.

For a meter-time request such as:

- 17:00–18:00

show the archive interval whose raw meter/logger period is 17:00–18:00 according to existing completed-period semantics.

Presentation should be conceptually:

- primary: `17:00–18:00 · Hour`
- secondary: `Local time: 17:55–18:55` when trustworthy.

If no trustworthy local mapping exists, omit or mark the secondary local time as unavailable rather than estimating it.

## Statistics UX and coverage model — Local time mode

Statistics must not invent fractional consumption when the requested real-time range cuts through archive buckets.

For a range such as previous day 10:00 to next day 12:00 with hour buckets shifted by about 55 minutes:

- the first overlapping hour bucket may be partial;
- a number of inner hour buckets may be fully contained;
- the final overlapping hour bucket may be partial.

Statistics should:

1. sum only fully contained buckets for exact totals;
2. show a simple coverage indicator;
3. explain partial edge coverage on demand;
4. never interpolate consumption within a bucket unless a future explicit evidence-backed method is introduced.

Preferred normal-language presentation:

- `Measurement coverage: 25 of 26 hours exact`
- secondary detail: `55 min at the beginning and 5 min at the end fall inside partially overlapping meter intervals.`

When no complete bucket is fully contained, do not show `0` as if it were measured consumption. Show a clear unavailable/exactness state and list the overlapping intervals.

## Statistics UX — Meter time mode

Statistics interprets requested ranges directly in raw meter time.

Where the requested meter-time boundaries align with archive bucket boundaries, the existing full-bucket calculation remains exact on that selected time basis.

Do not apply a real-time coverage warning merely because the corresponding real/local interval is shifted. The user explicitly chose meter time.

Existing safety rules still apply:

- do not interpolate missing buckets;
- do not subtract across meter replacement;
- do not combine incompatible granularity semantics;
- report actual gaps or unavailable data.

## Coverage states

For **Local time mode**, the UI should support at least these semantic states:

- `EXACT` — requested real range is fully represented by complete archive buckets;
- `PARTIAL_EDGES` — complete inner buckets plus one or both partial edge buckets;
- `OVERLAP_ONLY` — requested real range intersects archive data but contains no complete bucket;
- `GAP` — missing data exists inside the requested range;
- `UNRESOLVED_TIME` — archive data exists but a trustworthy UTC mapping is unavailable.

The wording shown to users should be friendly and non-technical. Technical detail may be available in an info/detail view.

Meter-time mode may reuse `GAP`/unavailable semantics where genuinely relevant, but it should not manufacture `PARTIAL_EDGES` solely from the difference between raw meter time and real time.

## Navigator rules

### Local time mode

- Navigator and custom-range controls accept local time in the meter-assigned timezone.
- Internally convert the requested range to UTC.
- Query archive intervals by derived UTC overlap/containment, not by raw meter logger time.
- History uses overlap semantics.
- Statistics exact totals use full-containment semantics unless a metric is naturally point-in-time rather than interval-based.
- Never silently snap the user's requested range to meter boundaries.

### Meter time mode

- Navigator and custom-range controls accept raw meter/logger wall-clock time.
- Query using raw archive period semantics.
- History/Statistics should behave consistently with the displayed primary meter-time axis.
- Do not first convert the request through UTC/local time.

## Granularity / Auto resolution

For v2.1 initial implementation, correctness is more important than aggressive mixed-granularity optimization.

A later `Auto` planner may combine Hour/Day/Month data to maximize exact coverage, provided that:

- intervals never overlap or double count;
- family/granularity semantics remain valid;
- finer data may be used at range edges;
- coarser data may be used in fully covered inner ranges;
- the resulting coverage remains explainable.

The planner must respect the selected app time basis and must not mix Local and Meter query semantics inside one result.

## DST / repeated local hours

Canonical UTC must disambiguate repeated local times at the autumn DST transition.

If two local intervals would otherwise appear identical, the UI may add explicit zone labels such as `CEST` / `CET` (localized appropriately) so users can distinguish them.

The SU flag must be preserved as evidence and tested against real W1 behavior before relying on it for identity or conversion.

In meter-time mode, repeated raw meter wall-clock intervals must remain distinguishable using the preserved evidence/record identity; do not collapse two physical archive records merely because their displayed wall-clock text matches.

## Meter replacement / discontinuities

Do not bridge real-time anchors across:

- meter replacement;
- On-Time reset/discontinuity;
- invalid Type-F time evidence;
- unresolved DST ambiguity;
- other evidence conflicts.

Such boundaries create separate time-resolution segments with their own quality state.

The global app time-basis preference remains global, but timezone assignment and raw meter clock evidence are per physical meter.

## Persistence / backup / migration implications

v2.1 design must explicitly cover persistence and portability for:

- raw meter/logger time evidence;
- SU/summer-time evidence;
- On-Time evidence;
- Android acquisition UTC anchors;
- meter-assigned IANA timezone and provenance;
- derived UTC intervals and quality/provenance where persisted rather than recomputed;
- global app time-basis preference if product policy chooses to back up user preferences.

The per-meter timezone assignment is part of the data interpretation contract and should survive a canonical `.qw1backup` restore.

A restore must not silently replace the backed-up meter timezone with the receiving phone's current timezone.

## Home Assistant contract

The Home Assistant integration should use the same canonical UTC timeline as the Android app's Local time mode.

Exported/connector data should expose absolute UTC interval timestamps, for example:

- `period_start_utc`;
- `period_end_utc`;
- measurement/value fields;
- `time_quality`;
- meter timezone where useful for display/context;
- optional raw meter-time fields for diagnostics.

Home Assistant must not use raw meter wall-clock time as the primary timestamp for statistics, automations or correlation with other sensors.

**The Android global `LOCAL` / `METER` display preference must not change the integration-facing UTC contract.**

A user choosing Meter time in the Android app is choosing a presentation/navigation mode, not redefining the canonical integration timeline.

## Safety / scope

This work is a time-model, persistence, presentation and query change. It does not by itself authorize changes to protected NFC/M-Bus/archive traversal behavior.

Before implementation:

- verify SU/DST semantics against protocol/manufacturer evidence and, if needed, real-device evidence;
- verify On-Time continuity behavior across archive depth and DST boundaries;
- audit Android ZoneId capture/persistence behavior without adding location permission;
- design DB migration and backup-schema evolution;
- add deterministic unit tests for hour/day/month boundaries, drift, DST, meter replacement, timezone assignment/change, unresolved anchors and partial coverage;
- decide whether migration of existing v2.0 archive rows can derive UTC safely or requires a fresh validated anchor/re-sync.

## UX scenarios that must be tested

At minimum:

1. Local mode: exact one-hour match;
2. Local mode: one-hour request crossing two shifted archive buckets;
3. Local mode: multi-hour request with partial start/end buckets;
4. Local mode: previous-day 10:00 to next-day 12:00;
5. Local mode: exact full-day request;
6. Local mode: request with a missing bucket in the middle;
7. Local mode: DST spring-forward;
8. Local mode: DST fall-back/repeated hour;
9. both modes across meter replacement;
10. unresolved/low-quality real-time mapping;
11. long-range statistics with Hour/Day/Month availability;
12. Meter mode: primary/secondary times are swapped correctly;
13. Meter mode: navigator/query uses raw meter time and does not apply local-time edge coverage;
14. first verified Live read assigns Android IANA ZoneId to a previously unassigned meter;
15. later phone timezone change does not silently alter the meter timezone;
16. explicit user timezone change updates derived presentation without rewriting raw meter time;
17. backup/restore preserves the meter-assigned timezone;
18. Home Assistant/export uses identical UTC boundaries regardless of Android `LOCAL` / `METER` preference.
