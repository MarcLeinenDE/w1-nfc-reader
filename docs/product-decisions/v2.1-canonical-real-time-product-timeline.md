# v2.1 product decision — canonical real-time product timeline

Date: 2026-09-12
Status: accepted for v2.1

## Decision

The normal W1 NFC Reader product UI exposes one canonical time axis: reconstructed real time.

For archive observations, canonical time is derived from the **single newest fully verified Live/default anchor for that physical meter** plus monotonic meter `ON_TIME`, then projected through the persisted per-meter IANA zone for LOCAL/civil presentation. Raw meter/logger wall-clock values remain lossless source evidence but are not a peer primary product timeline.

`ON_TIME` defines the geometry of the archive timeline. The active Live/default anchor defines only where that complete geometry sits on the real UTC axis. A newer verified anchor replaces the previous active anchor for projection; older anchors must never be selected independently for individual archive boundaries.

## User-facing consequences

- The former global `Local time / Meter time` selector is removed from normal Settings.
- Existing/restored development state that still contains `METER` as the old global preference is normalized back to `LOCAL` when a normal product Activity starts.
- Live observations use actual acquisition time as primary real time.
- Archive observations use the active verified anchor + `ON_TIME` reconstructed real interval as primary time.
- Raw meter/logger time remains visible where useful as secondary evidence and remains available in diagnostics/export/backup.
- The app must never silently use raw meter wall-clock as the primary normal timeline merely because real-time reconstruction is unavailable.
- If an archive interval cannot be reconstructed safely, fail closed and explain that real time is unavailable; raw meter/logger time may still be shown explicitly as raw evidence.

## Single-active-anchor contract

Per physical meter there is one active projection anchor:

- every accepted normal Live/default read can replace the active anchor when its `ON_TIME` is newer;
- the required verified final Default/Live read after each History family likewise refreshes the active anchor;
- all stored Hour/Day/Month/Year archive boundaries for that meter are projected backward from that same active anchor;
- native adjacent Hour boundaries that differ by exactly 3,600 `ON_TIME` seconds must therefore remain exactly 3,600 real-time seconds apart; the same principle applies to Day/Month/Year native durations;
- an archive `ON_TIME` newer than the active anchor is an invariant failure and is not resolved by falling back to another historical anchor;
- a backwards/reset `ON_TIME` must not silently replace the active timeline. It requires explicit generation/reset handling rather than guessing.

This supersedes the earlier boundary-by-boundary nearest-anchor selection. That older approach could stretch or compress one physical archive interval when its two boundaries happened to select different Live anchors.

## Why

The meter wall clock can drift relative to real civil time. Applying the current wall-clock offset retrospectively would also be unsafe because drift may change over the life of the meter. `ON_TIME` provides monotonic elapsed-time evidence; the newest verified Live/default anchor binds that elapsed-time axis to a real acquisition epoch. Using one anchor for the complete stored meter timeline preserves all native archive durations exactly and avoids artificial discontinuities at historical anchor handovers.

## Home Assistant / integration identity

**Canonical UTC must not be the deduplication identity.** A newer active anchor may legitimately shift the absolute reconstructed UTC position of older archive observations while leaving the underlying physical archive occurrence unchanged.

The app now contains the deterministic archive identity primitive `SourceRecordId`. It produces a versioned external ID in the form:

`w1:v1:<sha256>`

The SHA-256 input is a canonical length-prefixed sequence containing only meter-native occurrence identity:

- physical meter identity;
- archive family (`HOUR` / `DAY` / `MONTH` / `YEAR`);
- preserved raw logger timestamp;
- preserved native occurrence key, normally `OT:<on_time_seconds>` when valid `ON_TIME` exists.

The raw meter identity is therefore not exposed in the ID text itself, while a fresh phone that rereads the same physical archive occurrence deterministically regenerates the same `source_record_id`.

The ID deliberately excludes reconstructed UTC/local time, app database row IDs, retrieval timestamps, phone/install identity and measurement content. Therefore:

- changing the active time anchor cannot create a new source ID for the same physical occurrence;
- the same `ON_TIME` in different archive families produces different IDs;
- the same native occurrence on another meter produces a different ID;
- raw logger timestamp participates as collision protection if a meter ever reuses an `ON_TIME` value after a reset;
- legacy records without native `ON_TIME` remain deterministically identifiable through preserved logger occurrence evidence, but native `ON_TIME` remains preferred whenever available.

`SourceRecordIdTest` protects these invariants.

### Transport / deduplication responsibility

The Android app must **not** maintain an authoritative "already sent" ledger for Home Assistant. When the future HA transport is implemented, the phone may send every locally available eligible observation every time.

Home Assistant is the idempotence authority and must enforce a unique-key / UPSERT / ignore-known-ID contract on `source_record_id`:

- unknown ID -> insert;
- known ID with identical payload -> no-op/confirmation;
- known ID with improved derived metadata such as a better reconstructed UTC placement -> update the existing record, never create a duplicate.

This deliberately makes phone replacement and restore-free reinstall safe: a new phone can reread and resend the complete retained meter archive, and HA recognizes already-known physical occurrences from their deterministic IDs.

If a future real meter reset can reproduce both the same `ON_TIME` and the same raw logger occurrence under one unchanged physical meter identity, the integration must introduce an explicit meter-generation discriminator before accepting otherwise-colliding records. Do not derive that generation from phone-local state.

LOCAL labels remain derived from canonical UTC plus the persisted IANA zone. Raw meter/logger wall-clock remains an auxiliary attribute/evidence field and must not be exported as if it were canonical event time.

## Safety / evidence guardrails

- `ON_TIME` alone is not a civil timestamp; it requires the active verified anchor.
- Never extrapolate a newer archive boundary beyond the active verified anchor.
- Never invent UTC, a timezone or a fractional archive value.
- Preserve raw Type-F/logger time, `ON_TIME`, occurrence identity and all source evidence unchanged.
- No NFC command, mailbox traversal, parser or synchronization semantics are changed by this product decision.
- `QalcosonicReader.java`, `MbusParser.java` and validated archive traversal remain protected.

## Compatibility

The internal `AppTimeBasis.METER` path may remain temporarily for regression/diagnostic/backward-compatibility coverage while v2.1 is hardened, but it is no longer exposed as an equal normal-product setting. Old schema-3 development backups that contain the former preference remain readable; the normal UI returns to the canonical reconstructed real timeline.

Older time-model databases/backups that contain several verified anchors remain readable. Projection exposes only the newest active anchor per meter; the next accepted anchor write or import normalization collapses the stored state to one active anchor per meter.
